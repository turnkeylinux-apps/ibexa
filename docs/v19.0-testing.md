# Ibexa 19.0 testing

## Scope and dependency decision

Debian 13 Trixie does not provide Ibexa. The appliance installs maintained
Ibexa Open Source v4.6.32 LTS from the official `ibexa/oss-skeleton` Git tag
and pins release commit `bcd755b140abbf72a19c2231360a82b3f3408a1f`.
Ibexa 4.6 is maintained through February 2027 and receives security fixes
through February 2029. It supports the PHP 8.4 and Node.js 20 versions shipped
by Trixie. The newer Ibexa 5.0 line requires Node.js 22, so using 4.6 keeps the
appliance on a maintained upstream LTS while preserving the Debian-first
dependency policy.

PHP 8.4, MariaDB 11.8, Apache, Composer, Node.js 20, Yarn 4.1 and PHP
extensions come from signed Debian Trixie repositories. Composer installs the
exact upstream dependency graph in `composer.lock` and the normal Ibexa asset
build completes with Debian's `yarnpkg` executable.

Ibexa updates are supervised because upstream updates can include Composer,
database and application changes. Administrators should follow the official
Ibexa 4.6 update procedure. The non-mutating update check used for acceptance
queries official `v4.6.*` release tags and runs:

```sh
composer --working-dir=/var/www/ibexa outdated --direct --locked
composer --working-dir=/var/www/ibexa audit --locked --no-dev --abandoned=ignore
```

## Preflight evidence

A disposable Trixie container completed the normal Ibexa install, including
59 schema queries, 30 clean-data queries, repository indexing, GraphQL schema
generation, Composer production installation and the full Yarn Encore asset
build. Apache served the application over HTTPS. The firstboot administrator
authenticated through the CSRF-protected login form. A folder was created and
published through Ibexa's repository API, returned by authenticated REST after
an Apache reload, and found directly in MariaDB by its remote ID.

The preflight found one appliance issue: updating the administrator password
directly in MariaDB left the old credential in the production cache. The v19
firstboot hook now clears that cache after updating the password and email.

## Known limitations and deferred issues

- Docker acceptance does not exercise the installer, appliance kernel,
  bootloader or physical hardware. Ibexa adds no appliance-specific behavior
  at those boundaries, so the validated Core 19 baseline supplies inherited
  evidence.
- Ibexa 4.6's locked dependency graph includes packages that Composer marks
  abandoned, although its advisory audit currently reports no known security
  vulnerability advisories. These are upstream-managed dependencies within a
  supported Ibexa LTS, not appliance substitutions.
- The focused round trip covers administrator authentication and ordinary
  folder content. Media workflows, custom content types, external search and
  outbound mail delivery require optional configuration and are outside the
  primary appliance flow.
